# AI 起名平台

实验三的完整交付：一个部署在 Vercel 的 Node 网页应用，支持多模型切换、流式输出、Supabase 起名历史。

## 线上地址

- 生产环境：https://ai-naming-platform-alpha.vercel.app
- GitHub 仓库：https://github.com/xiefeiyue001/ai-naming-platform
- Supabase 项目：ai-naming-platform（东京区域）

> 说明：`*.vercel.app` 在中国大陆网络下常被解析到黑洞地址（如 159.106.121.75），直连会超时。如需在国内直接打开，需要代理，或给项目绑定一个自己的域名。项目本身从境外节点访问一切正常（已用 Supabase 数据库的 pg_net 扩展实测首页与接口均返回 200）。

## 技术要点

1. **一套调用代码适配所有模型**：`api/name.js` 里的 `modelConfigMap` 只放 `baseURL`、`apiKeyEnv`、`model` 三个配置项，请求逻辑只写一份，新增模型只加一条配置。
2. **流式输出**：上游 `stream: true`，后端逐片解析 SSE 的 `delta.content`，再用 `text/event-stream` 转发给前端；前端用 `ReadableStream` 边收边渲染。
3. **密钥不落代码**：全部通过环境变量读取（`SUPABASE_URL`、`SUPABASE_ANON_KEY`、`SUPABASE_SERVICE_ROLE_KEY`、`DEEPSEEK_API_KEY`…），`.env` 在 `.gitignore` 里。
4. **历史归档**：生成结束后把「需求 / 方案 / 模型」写入 `name_history` 表，服务端使用 `service_role` key 绕过 RLS 写入；页面通过 `/api/history` 读最近 20 条。
5. **降级可用**：未配置 Supabase 时起名功能照常返回，只是不存档；未配置某模型密钥时返回明确提示。

## Supabase 建表

执行 `sql/name_history.sql` 即可，核心表结构：

```sql
create table public.name_history (
  id bigint generated by default as identity primary key,
  user_requirement text not null,
  name_result text not null,
  model_name text not null,
  created_at timestamptz default now()
);
```

调试期用「anon 可插入、可读取」策略即可；正式上线建议把读写都收回到服务端（service_role key），或按 `user_id` 维度收紧 RLS —— 详见 `sql/name_history.sql` 第 4 段。

## 思考题参考答案

**1. 流式输出和一次性返回全部文字有什么区别？**
一次性返回要等模型把全部 token 生成完才发一个完整响应，首字延迟等于总生成时间，长回答时页面会长时间空白；流式输出（SSE）在生成第一个 token 时就开始推送，用户能立刻看到内容增长，首字延迟从「几秒~几十秒」降到「几百毫秒」，体验更好，也便于中途停止、节省 token。代价是响应变成一条长连接，前端要自己解析分片、处理中断与错误。

**2. 使用 modelConfigMap 统一配置模型有什么好处？**
把「地址、密钥来源、模型名」这些易变信息集中成数据，调用逻辑只保留一份：新增模型只加配置不改主代码，降低重复代码和改动风险；切换/回滚模型是改配置而不是改逻辑；密钥统一走环境变量，避免散落在多个调用分支里；出问题时排查点也只剩一处（核对 baseURL 与鉴权）。本质上是用配置驱动替代分支驱动，符合开闭原则。

**3. 平台文档里有 curl 和 OpenAI SDK 两种示例，本次实验为什么优先选 curl？**
curl 展示的是完整的 HTTP 请求：URL、鉴权头、body、`stream: true` 参数一目了然，能看清「一次调用到底发了什么」，排错时可以直接拿它逐项对照；SDK 把请求细节封装起来，写起来省事但看不到底层，出问题（比如地址写错、stream 没开、字段名不对）不好定位。入门阶段先用 curl 建立对协议的直观认识，熟练后再用 SDK 提高效率。

**4. 这个项目中 AI 起到了什么赋能作用？**
AI 承担了从「需求」到「可运行产品」的整段实现：按提示词一次生成前端页面、两个 Serverless 接口和建表 SQL，把跨三个平台（Supabase / GitHub / Vercel）的配置串起来；人只需要给出约束（流式、3 组名字带寓意、密钥走环境变量、多模型可切换）并做验收与排错。它把原本需要查文档、拼代码、反复试错的工作压缩成「描述需求 + 审查结果」，让非专业开发者也能完成一个带数据库、带外网访问的完整应用。
